# Plan 132-03 — Bleed-safe enrichment for the 4 Pima cities

**Mode:** standard
**Goal:** Give every General Fund category the four cities loaded (132-02) a human-readable, bleed-safe enrichment so icicle leaves + category chips explain themselves. Build `scripts/loadPimaEnrichment.mjs`, deriving the worklist **live from the loaded `budget_categories`** across all four cities, reusing existing universal coverage (much already exists from Tucson v2.17), authoring universal rows only where the label is genuinely shareable and city-scoped rows otherwise, written NULLS-DISTINCT-safely at $0.

Depends on 132-02 (categories must be loaded). No paid AI. No schema change.

<threat_model>
**T-132-03 — Authoring shared-scope enrichment that bleeds across every entity.**
- *Surface:* writes `treasury.category_enrichment`, some with `municipality_id = NULL` (universal — shown for that `name_key` on EVERY entity).
- *Threats:* (a) a universal row with city-specific/dollar text bleeding into unrelated entities (the Phase-scoping-fix incident, [[project_enrichment_scoping_fix]]); (b) duplicate universal rows under the NULLS-DISTINCT index; (c) incomplete coverage leaving loaded categories unexplained; (d) an accidental paid-API call.
- *Mitigations:* universal text stays generic (no `$`, no city names); anything specific scoped to the city's `municipality_id`; universal rows **delete-then-insert** (not upsert) per NULLS-DISTINCT ([[reference_category_enrichment_nulls_distinct]]); derive the worklist from the live loaded set and assert 100% coverage; **inline authoring only, zero API calls** ($0).
- *Block on:* high (a universal bleed corrupts enrichment app-wide).
</threat_model>

## Tasks

<task id="132-03-01" type="execute">
<action>
Create `scripts/loadPimaEnrichment.mjs` (dry-run by default; `--apply` to write), modeled on `scripts/loadTucsonEnrichment.mjs`. (1) Load `.env`/`.env.local`; `createClient` on the `treasury` schema. (2) Resolve the four municipality_ids by (name in {Oro Valley,Marana,Sahuarita,South Tucson}, state='AZ', entity_type='city'). (3) Derive the LIVE worklist: those cities' `budgets` rows for `dataset_type IN ('operating','revenue')` across ALL loaded FYs → their `budget_categories` (depth 0 AND depth 1) → the distinct set of `link_key` (fallback lowercased trimmed `name`). Paginate past the 1000-row cap. (4) For each key, FIRST check whether a matching `category_enrichment` row already exists (universal OR for that city) — if so it is already covered (reuse Tucson-era universals). For uncovered keys, author a record: generic shareable concepts (`public safety`, `general government`, `debt service`, `highways and streets`, `culture and recreation`, `charges for services`, `taxes`, `intergovernmental`, `licenses and permits`, `fines and forfeitures`, `capital outlay`, etc.) as **universal**; ambiguous/city-specific labels (e.g. `redevelopment and housing`, `economic development`, or town-specific fund names) as **city-scoped** to whichever city carries them. Text generic for universal rows (no `$`, no city name). (5) Dry-run prints the full mapping (key → scope → covered-already? → text preview) + a coverage line `covered/total` per city and overall. No writes, no API calls.
</action>

After applying, re-derive the live worklist for all four cities and assert every key resolves to at least one matching `category_enrichment` row (universal or that-city-scoped): coverage == 100% per city. Run `--apply`, then a second time to confirm idempotency (0 net new rows). Spot-check that no universal row written this run carries city-specific / dollar text (bleed check), and that Tucson's existing enrichment is unaffected.
</action>

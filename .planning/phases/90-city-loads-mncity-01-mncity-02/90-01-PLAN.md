<objective>
Build the Phase 90 bulk-load tooling: add a roster helper `enumerateEntities(workbook)` to the Phase 89 loader, then add a **batch driver** `scripts/loadMNOSABatch.js` that — for one fiscal year — opens the single all-cities workbook, enumerates every city, and iterates the proven Phase 89 `importEntity` write path over the whole roster (per-entity GAAP/Cash basis from `GAAPInd`, per-FY population, per-FY source_url, never-overwrite guard).

No live bulk load happens in this plan — prove the whole roster parses via `--dry-run` and lock the behavior with offline tests. The live FY2012–2023 sweep + in-phase verification + the committed basis/residual files are plan 90-02.

Mirror `scripts/loadOhioAOSBatch.js` (the proven all-cities batch analog): its `enumerateCities` → loop-over-the-single-entity-write-path shape is exactly MN's — but SIMPLER. MN has ONE workbook per FY with the accounting basis in the per-row `GAAPInd` column, so there is **NO GAAP→CASH→MOD precedence assignment** (drop that whole branch); every city in the one workbook is loaded under its own row's basis.
</objective>

Reused verbatim from scripts/loadMNOSA.js (Phase 89, shipped + verified):
- `importEntity(supabase, workbook, opts)` where opts = `{ entityName, fiscalYear, sourceUrl, sourceDate, dryRun, entityType }`. Returns a summary `{ entityName, fiscalYear, basis, entityType, operatingTotal, revenueTotal, population, county, expFunctions, revGroups }`; with `dryRun:true` it does the full parse and returns the summary WITHOUT touching Supabase. This is the loop body.
- `resolveSourceUrl(fiscalYear, 'city')` → the per-FY city_url from scripts/mnOsaDatasets.json (null if not in the manifest).
- `getSupabase()` — createClient with the SUPABASE_SERVICE_KEY guard; never called in --dry-run.
- `entityBasis(workbook, name, 'city')` → 'GAAP'|'Cash' from the row's GAAPInd column.
- `cellText`, `cellNum`, `normalizeLabel` — cell + label helpers. The tree-map (loaded internally) gives `identity_labels.entity_name`, `revenue.total_label` ("Total Revenues"), `expenditure.total_label` ("Total Expenditures"), `header_row`, `data_start_row`.

New in this plan:
- `enumerateEntities(workbook)` (EXPORT from loadMNOSA.js): open the `Governmental Funds` sheet; from `data_start_row` down the `Entity Name` column, collect every non-empty entity name whose row has a finite, non-zero `Total Revenues` OR `Total Expenditures` (skips blank/footer rows). Return an array of names in sheet order. (Analog of Ohio's enumerateCities, minus the layout/precedence machinery — MN has one sheet, header row 1.)
- `scripts/loadMNOSABatch.js` — the driver (see tasks). Acquisition: if `--file` given use it; else `resolveSourceUrl(fy,'city')` + download to `_mn-recon/cired_<YY>_data.xlsx` if absent (curl). _mn-recon/ is already gitignored (Phase 89).

NO basis precedence (the Ohio difference): MN's workbook is the single source for the FY; each city is loaded under its own GAAPInd basis. The "basis distribution" is just a tally of how many cities are GAAP vs Cash for that FY (for the SUMMARY + the 90-02 mnCityBasis.json).

Source-gap residual (D-03): cities whose Entity Name row exists but whose Total Revenues AND Total Expenditures are both blank/zero (filed nothing) — report them, do NOT write them (no phantom municipalities). Distinct from cross-FY coverage, which 90-02 accumulates across years.

CLI (parseArgs), mirror loadOhioAOSBatch.js shape (minus the per-basis flags):
`node scripts/loadMNOSABatch.js --fy <YYYY> [--file <path>] [--limit N] [--dry-run]`

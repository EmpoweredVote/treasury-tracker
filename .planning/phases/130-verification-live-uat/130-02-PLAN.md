# Plan 130-02 — TUC-09: tether verdict pre-determination

**Mode:** standard
**Goal:** Turn the tether check into a *confirmation* instead of a guess (D-09). Before Chris looks at the live banner, compute what the Essentials tethered icon *should* do for Tucson and Pima County by fetching the live `coverage.json` and running the same deterministic matcher the app uses. This yields a definitive covered/not-covered verdict (and guards against a silent match/fetch bug — a mismatch between prediction and live render is itself a finding). If Essentials doesn't yet cover Tucson/Pima, this plan documents it as an expected cross-repo coverage gap with a concrete fix pointer (D-10) — no TT code change either way.

Reusable asset: `src/utils/essentialsCoverage.ts` — `matchEntityToCoverage(entity, catalog)` is pure + deterministic; `fetchCoverage()` targets `ESSENTIALS_URL` (`https://essentials.empowered.vote`) and returns `null` on failure. The probe mirrors this logic in a small Node script (the util is browser/ESM+Vite `import.meta.env` code, so the probe ports the matcher rather than importing the module directly).

<threat_model>
**T-130-02 — Consuming untrusted remote catalog data in the probe.**
- *Surface:* the probe fetches `coverage.json` from a remote origin and reads `label`/`geoids`/`state` fields.
- *Threats:* a malformed or hostile body causing the probe to crash (masking the real verdict) or to emit a false "covered" result.
- *Mitigations:* mirror `isValidCatalogShape` (object + array-typed known fields) before matching; the probe only reads + reports plain data (no URL/DOM/href construction — matching the module's T-125-01 note); treat any parse/shape failure as "fetch failed", never as "covered". Read-only; no DB access; no writes to production.
- *Block on:* none (read-only, off-repo) — but a probe crash must surface as "fetch failed", not a silent pass.
</threat_model>

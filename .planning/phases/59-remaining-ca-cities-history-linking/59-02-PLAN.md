# Plan 59-02 — county linking + entities + Test deletion

**Mode:** standard
**Goal:** Execute **Step 2** of `docs/socal-county-onboarding.md` for the remaining CA cohort: create the 4 missing linking-only county nodes and link the 5 county-bound unlinked cities via `scripts/seedCountyLinks.js`, resolve San Francisco as a single combined city-county node per the D-07 research finding (no separate county node), and delete the budget-less "Test" record (D-08). Satisfies ENR-02 and success criteria #2 + #3 + #4.

**Why SF is special — NO "San Francisco County" node (verified, D-07 research flag RESOLVED):** the breadcrumb (`src/App.tsx:539-564`) and Cities-in-County panel (`src/components/CitiesInCountyPanel.tsx:16-18`) both derive the county hop purely from `municipalities.county_id`, with no special-case for a consolidated city-county. Linking SF to a separate "San Francisco County" node would render the redundant chain **US / California / San Francisco County / San Francisco** and a self-listing panel. So SF stays a single `entity_type='city'` muni with **`county_id = NULL`** → breadcrumb renders **US / California / San Francisco**, cleanly. This reduces D-05's literal "5 county nodes" to **4** (SF removed). See `59-RESEARCH.md` §D-07. (Optional, executor discretion: rename the muni to "City and County of San Francisco" for label honesty — structural shape is unchanged either way.)

**Why this never touches budgets (verified, D-06):** `seedCountyLinks.js` only writes `municipalities.county_id` and creates county entities with `treasury_ensure_municipality(... p_entity_type='county', p_population:0)` — it never writes a budget row (:154-163). It reuses an existing county entity (Alameda) rather than duplicating, links only NULL-or-same-county cities, and does NOT repoint a city linked to a different county unless `--force` (which we do NOT pass) (:144-152). `loadCountyBudget.js` is intentionally NOT run — the 4 new nodes are linking-only "groupers", matching the existing Alameda/Sacramento/San Diego precedent; county-gov budgets are v2.4.

**The link map (D-06):** Bakersfield→Kern (new), Fresno→Fresno (new), Oakland→Alameda (existing), Riverside→Riverside (new), San Jose→Santa Clara (new). San Francisco = combined node (no link). The 4 already-linked other-county cities (Berkeley, Fremont, Sacramento, San Diego) need history (Plan 59-01), not linking.

<threat_model>
**T-59-02 — Linking repoints a city to the wrong county, creates a confusing SF self-nest, an unintended county node gets a budget, or the Test deletion cascades into real data.**
- *Surface:* `seedCountyLinks.js` writes `county_id` via the service-role key and derives membership from the SCO `county` field — it links EVERY NULL-county DB city in that county's SCO membership, not only the named target. A raw DELETE of "Test" via the service key could cascade.
- *Threats:* (1) an unintended NULL-county DB city gets pulled into a link (blast radius beyond the target); (2) an already-linked city repointed (would need --force — must not pass it); (3) a "San Francisco County" node accidentally created (D-07 violation); (4) a new county node accidentally given a budget; (5) the Test deletion removes a record that actually has dependent budget/salary rows.
- *Mitigations:* (1) **dry-run each county first** and confirm the "Would link" list contains ONLY the intended target city before the real link (task 02 gates task 03); (2) never pass `--force`; (3) never run seedCountyLinks for "San Francisco" — SF handled explicitly in task 04, and task 05 asserts no SF county node exists; (4) never run loadCountyBudget.js — task 05 asserts the 4 new nodes have zero budget rows; (5) Test deletion is gated on a dependent-row check (task 06) — delete only if zero dependents, else document.
- *Block on:* high. Do not run any real link (task 03) until that county's dry-run (task 02) shows only the intended city in "Would link". Do not delete Test (task 06) until the dependent-row check returns zero.
</threat_model>

# Plan 59-01 — SCO history layering beneath the thin CA cities (FY2003 reach)

**Mode:** standard
**Goal:** Execute **Step 1** of `docs/socal-county-onboarding.md` in **city-targeted** form for the 7 thin custom-source CA cities, layering SCO all-governmental-funds operating + revenue FY2003→latest BENEATH their existing custom years via per-city `scripts/bulkLoadStateController.js --city "<name>"` runs. This is the Phase 58 Long Beach / West Hollywood layer-beneath pattern (prior D-04), city-targeted per CONTEXT D-04 — NOT a county expansion. Satisfies HIST-02.

**Why city-targeted, not county (verified, D-04 research flag RESOLVED):** `bulkLoadStateController.js` supports `--city <entity_name>` (parse :184, `cityFilter` :194). With `--city` set the SCO `$where` becomes `entity_name='<city>' AND fiscal_year='<fy>'` (:218-220) — the county field is ignored, so exactly one city loads. Full-county SCO expansion stays deferred to v2.4. **No new tooling — the filter already exists.** See `59-RESEARCH.md` §D-04.

**Why layering is safe (verified, D-01):** the loader writes `data_source = "CA State Controller - ${label}"` (:41); `findConflictingBudget` (:87-101) preserves any existing row whose `data_source !== ` that label. So a layered city's custom rows (a *different* source) are SKIP-logged and untouched, and SCO only writes the (fiscal_year, dataset) slots the city had no row for. Every write passes `p_source_url = ds.pageUrl` (`/d/<id>`) + `p_source_date` (:159-169) — always-sourced.

**The cohort (D-01 thin-vs-rich, see 59-RESEARCH.md):**
- **Layer SCO (7 thin):** San Francisco (custom FY2025–26), Oakland (GP op-only FY2024–25), Fresno (GF op-only FY2020–26), Riverside (GF op-only FY2023–26), Bakersfield (custom FY2025–26), San Diego (custom FY2025), Berkeley (custom FY2012–15).
- **Leave custom-only (3 rich) — DO NOT TOUCH:** San Jose (GF op+rev FY2021–25), Fremont (op+rev FY2019–26), Sacramento (op+rev FY2013–26).

**Load shape:** per-city, dry-run-first. Each city is one `entity_name` × ~22 years — small, far below the 600s timeout that forced 58-01's chunking; still pin `--source-date 2026-06-16` and split a slow city into year-chunks. Idempotent on (municipality_id, fiscal_year, dataset_type) — any run is re-runnable. SF / Fresno / Riverside / San Diego names also exist as SCO **county** entity_names — the per-city dry-run is the guard against loading a county row by mistake (D-04 caveat).

<threat_model>
**T-59-01 — A city-targeted load clobbers a custom-source city's data, writes unsourced rows, touches a rich custom-only city, or loads a county-level row under a city name.**
- *Surface:* `bulkLoadStateController.js` writes budget rows via the service-role key. A `--city` value that matches an SCO county entity_name, or a label collision, could corrupt or misattribute data.
- *Threats:* (1) silent loss/overwrite of a layered city's custom rows (SF/Oakland/Fresno/Riverside/Bakersfield/San Diego/Berkeley); (2) layered rows left with NULL source_url (always-sourced violation); (3) a rich custom-only city (San Jose/Fremont/Sacramento) accidentally loaded; (4) a county-level SCO row loaded under a same-named city (Fresno/Riverside/SF/San Diego); (5) a 0 population breaking per-capita.
- *Mitigations:* (1) **per-city baseline probe** of every layered city's custom rows (data_source + fy set + totals) captured BEFORE any write and re-checked AFTER (tasks 01 + 04); (2) **dry-run per city** confirms exactly that city's rows return with plausible per-capita-scale totals (not county-scale) before any real load (task 02 gates task 03); (3) never run the loader for San Jose/Fremont/Sacramento — verified untouched post-load (task 04); (4) every write passes durable `/d/<id>` source_url + source_date 2026-06-16; (5) population backfill is write-only on 0/NULL.
- *Block on:* high. Do not run a real load for any city (task 03) until that city's dry-run (task 02) returned the city (not the county) with plausible totals AND the task-01 baseline is captured.
</threat_model>

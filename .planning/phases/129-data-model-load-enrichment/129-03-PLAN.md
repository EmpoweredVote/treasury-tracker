# Plan 129-03 — Bleed-safe Tucson category enrichment

**Mode:** standard
**Goal:** Give every General Fund category Tucson loaded (Plan 129-02) a human-readable, bleed-safe enrichment so the icicle leaves and category chips explain themselves. Build `scripts/loadTucsonEnrichment.mjs`, deriving the worklist **live from the loaded `budget_categories`** (so coverage is provably 100% of what shipped), authoring universal rows where the label is genuinely shareable and Tucson-scoped rows otherwise, written NULLS-DISTINCT-safely at $0.

Depends on 129-02 (categories must be loaded first). No paid AI. No schema change.

<threat_model>
**T-129-03 — Authoring shared-scope enrichment that bleeds across every entity.**
- *Surface:* writes `treasury.category_enrichment` rows, some with `municipality_id = NULL` (universal — shown for that `name_key` on EVERY entity).
- *Threats:* (a) a universal row containing Tucson-specific or dollar-specific text bleeding into unrelated cities/states (the Phase-scoping-fix incident); (b) duplicate universal rows from an upsert against the NULLS-DISTINCT index; (c) incomplete coverage silently leaving loaded categories unexplained; (d) an accidental paid-API call.
- *Mitigations:* keep universal text generic (no `$`, no city/entity names) and scope anything specific to Tucson's `municipality_id`; write universal rows **delete-then-insert** (not upsert) to respect NULLS-DISTINCT; derive the worklist from the live loaded set and assert 100% coverage before finishing; **inline authoring only — zero API calls** ($0).
- *Block on:* high (a universal bleed corrupts enrichment for the whole app).
</threat_model>

## Tasks

<task id="129-03-01" type="execute">
<action>
Create `scripts/loadTucsonEnrichment.mjs` (dry-run by default; `--apply` to write), modeled on `scripts/loadSoCalEnrichment66.mjs`. (1) Load `.env`/`.env.local` and `createClient` on the `treasury` schema. (2) Resolve Tucson's municipality_id by (name='Tucson', state='AZ', entity_type='city'). (3) Derive the LIVE worklist: Tucson's `budgets` rows for `dataset_type IN ('operating','revenue')` across ALL loaded FYs → their `budget_categories` (depth 0 and depth 1, so both the icicle parents like `Current`/`Debt service` and their leaf functions/sources are covered) → the distinct set of `link_key` (fallback lowercased trimmed `name`). Paginate past the 1000-row cap. (4) For each worklist key author an enrichment record: reuse a generic concept for shareable labels (e.g. `public safety`, `general government`, `debt service`, `charges for services`, `taxes`) as **universal**; author Tucson-specific labels (era-specific or ambiguous, e.g. `Non-Departmental`, `Community enrichment and development`) as **Tucson-scoped**. Text must be generic for universal rows (no `$`, no "Tucson", no other city). (5) Dry-run prints the full mapping (key → scope → text preview) and a coverage line `covered/total`. No writes and no API calls in dry-run.
</action>

<task id="129-03-02" type="execute">
<action>
Add the `--apply` write path to `scripts/loadTucsonEnrichment.mjs` and run it. Universal rows (`municipality_id = NULL`): **delete-then-insert** per `name_key` (delete the existing universal row for that `name_key` where `municipality_id IS NULL`, then insert) — NOT an upsert on `(name_key, municipality_id)`, which duplicates under the NULLS-DISTINCT index. Tucson-scoped rows (`municipality_id = <Tucson id>`): upsert on `(name_key, municipality_id)` is safe. After applying, re-derive the live worklist and assert every key now resolves to at least one matching `category_enrichment` row (universal OR Tucson-scoped) — coverage must be 100%. Run `--apply`, then run it a second time to confirm idempotency (0 net new rows).
</action>

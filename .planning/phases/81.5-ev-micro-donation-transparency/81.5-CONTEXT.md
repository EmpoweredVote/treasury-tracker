Explored + scoped conversationally with Chris on 2026-06-23 (no separate discuss-phase pass needed). Authoritative background in auto-memory:

## The problem
The EV nonprofit financials view shows only platform totals (Benevity $1,475 / GiveButter $703 / Patreon $370 for FY2026) + a goal bar. That hides the actual story: EV is sustained by recurring monthly micro-donations from like-minded people. Benevity even *misleads* — its 58% looks like "one big source" but is one donor's matched recurring giving.

## Locked decisions
- **Framing:** invite-forward, celebrate the recurring micro-donation *model* — NOT smallness/purity, NOT "all-volunteer = no money needed."
- **Locked headline copy (Chris's words):** "These tools are free for everyone, and always will be. We are currently sustained by like-minded people who give a few dollars a month."
- Under it: a quiet recurring-supporter stat + a soft "Join them" recurring-donate invite. Never a hard sell; $2/mo celebrated; "more if you can afford it."
- **Honesty (hard rule):** never lie/stretch. The word "currently" is deliberate — true today, leaves the bridge-funding door open. Never imply EV refuses larger/grant support.

## Data realities (verified from `data/ev-sources/` exports, FY2026)
- Per-donation amounts already exist in the platform export CSVs `loadEVDonations.js` reads; the distribution is currently discarded (only gross/fee per source persisted; `item_count` placeholder = 1).
- **Benevity = 1 donor (Chris Andrew), 61 matched recurring rows → count as ONE supporter, never 61.**
- GiveButter = 43 recurring-plan charges from ~14 distinct donors (per-donor median ~$36).
- Patreon = recurring patrons (335 event rows; distinct-patron count still to be computed honestly).
- Largest single gift all year: $500. Typical gift ~$20.
- **Privacy:** Benevity + GiveButter exports contain donor names/emails/addresses. Persist ONLY anonymized aggregates — never per-donor rows/PII.

## Persistence approach (DECIDED — lean, single-repo)
Chris chose the **lean** path (2026-06-23): no backend change, treasury-tracker only. The frontend reads everything via the EV-Accounts API (`../EV-Accounts/backend`), but the **budgets/categories endpoint is already consumed** and returns `item_count`, `description`, `why_matters`, `actual_amount` per category. So we **ride existing returned fields on the "Donations" category** (link_key `donations`) rather than adding backend fields:
- `item_count` on Donations = **distinct active recurring-supporter count** (honest, semantic).
- A compact anonymized aggregate JSON (typical monthly, size buckets) written into the Donations `description` field as the lean carrier; frontend parses + renders. Documented as an intentional lean tradeoff.
- Written by an extended `scripts/loadEVDonations.js`; manual-refresh, consistent with existing EV loads (not live).
- Full structured backend fields (richer chart) remain a future option if desired.
No `org_financial_summary` schema change; no EV-Accounts backend change; one deploy (Netlify) + the Supabase data write.

## Out of scope
- Any per-donor display or stored PII.
- Changing the Donate button/modal (kept as-is).
- Hard-sell / pledge-drive UX.

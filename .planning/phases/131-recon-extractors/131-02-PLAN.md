# Plan 131-02 — `scripts/extractAcfrGF.py` (generalized GF extractor)

**Mode:** standard
**Goal:** Generalize the proven Tucson extraction engine into a **city-agnostic** extractor that turns any Pima-municipality ACFR PDF into the two General Fund trees (revenue-by-source; 2-level expenditure-by-function) and **self-ties** each to the printed GF total at $0. This is the only genuinely new code in the milestone. It consumes the per-city windows + statement structures locked in Plan 131-01 and produces the trees Phase 132 loads via `treasury_sync_budget_tree`.

**Key generalization:** unlike `extractTucson.py` (whose tree grouping reflects Tucson's function vocabulary), `extractAcfrGF.py` **derives the 2-level structure from each statement's own printed sub-total rows** (`Total Current`, `Total Debt service`, `Total capital outlay`, etc.), so a small town with a simpler/different function set extracts correctly without per-city code. `extractTucson.py` is left untouched — the shipped `processTucson.js` pipeline keeps depending on it, so blast radius is zero. Tucson is used only as a **regression oracle** here.

No seed, no live load, no schema touch — the extractor only reads local PDFs and prints JSON.

<threat_model>
**T-131-02 — Parsing network-sourced PDFs; a malformed/hostile PDF could produce wrong-but-plausible numbers or inject via the subprocess.**
- *Surface:* `extractAcfrGF.py` shells out to `pdftotext` and parses its text output into financial trees Phase 132 loads into the app-facing `treasury.budgets`.
- *Threats:* (a) command injection via a crafted path/filename; (b) a mis-parsed row silently producing a tree that looks right but is wrong; (c) column bleed from an adjacent fund / Total column inflating GF numbers; (d) over-generalization — a heuristic that ties Tucson but silently mis-groups a town whose statement labels differ.
- *Mitigations:* invoke `pdftotext` with an **args array** (`subprocess.run([...], shell=False)`), paths as list elements (no interpolation); make the **$0 `tie_delta` the hard gate** — a non-zero delta exits non-zero so a mis-parse can never pass downstream; read GF strictly as the **first data column**; validate every derived parent sub-total equals the sum of its children (independent second tie catching column bleed AND mis-grouping); require the **Tucson FY2024 regression tie** to pass so the generalization is proven against a known-good statement.
- *Block on:* high (the tie gate + the sub-total tie + the Tucson regression). A tree that does not tie $0 must not be emitted as valid.
</threat_model>

<task id="131-02-02" type="execute">
<action>
Implement the trees. **`--mode revenue`:** flat GF revenue-by-source tree from the printed source rows (label-driven, not count-locked); capture printed `Total revenues` as the tie target, exclude it from leaves. **`--mode operating`:** 2-level GF expenditure tree whose parents + children are **derived from the statement's own printed structure** — detect parent/sub-total rows (`Total Current`, `Total Debt service`, `Total capital outlay`, `Total capital projects`, or whatever the statement prints), attach the rows between a section header and its `Total <section>` line as that parent's children, and emit any standalone top-level expenditure leaf (e.g. `Capital outlay`) directly. Capture printed `Total expenditures` as the tie target; exclude all sub-total/bookend rows from the tree. Emit JSON `{ fiscal_year, mode, tree, computed_total, printed_total, tie_delta }`. `tie_delta = computed_total − printed_total`; if non-zero, print offending rows to stderr and exit non-zero. For operating mode, assert each derived parent's printed sub-total equals the sum of its children (report mismatch → non-zero exit).
</action>
<read_first>
- scripts/extractTucson.py (how revenue vs operating trees are shaped + returned; the sub-total assertion pattern)
- .planning/phases/131-recon-extractors/131-RECON.md (per-city/per-FY printed Total revenues / Total expenditures to tie against; per-city statement structure)
</read_first>
<acceptance_criteria>
- `--mode revenue` emits a flat source tree + `tie_delta == 0` against printed Total revenues for a sampled in-scope city×FY
- `--mode operating` emits a 2-level tree whose parents/children were derived from the statement's own sub-total rows (NOT a hardcoded list), + `tie_delta == 0` against printed Total expenditures
- Each derived parent sub-total == Σ its children; bookend/sub-total rows (`Total revenues`, `Total expenditures`, `Total <section>`, `Excess...`) appear in NO leaf
- Feeding a corrupted total (or dropping a row) yields a non-zero `tie_delta` AND a non-zero exit code (fail-loud verified)
</acceptance_criteria>
</task>

# Phase 71.1: Code Review Report

**Reviewed:** 2026-06-20T00:00:00Z
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

Reviewed the new `--rollup` single-scan BigQuery ETL added in Phase 71.1 to remediate
the 2026-06-19 per-(entity,FY,type) full-table-scan cost incident (~$132/day). The
review focused on the five risk areas called out: cost-safety, PII exclusion, SQL
parameterization, idempotency/never-overwrite, and caps.

**Strong points (verified):**
- The rollup query is correctly parameterized (`IN UNNEST(@entities)`, no string
  interpolation of entity/FY/type). FY/type are query literals but constant, not
  user-supplied. (SQL injection: not present.)
- PII exclusion holds: `ROLLUP_QUERY` projects only the 6 non-PII columns + `SUM(amount)`,
  and `groupRollupRows` -> `buildTree`/`buildSalaryTree` read only `fund1/org1/cat1/amount`,
  so even PII-laden input rows are dropped. Tests assert both.
- The dry-run-first flow is correct: a free `dryRun:true` job always runs before any billed
  scan, and the billed scan is gated on `isConfirm && fitsUnderQuota`.

**Key concern (cost-safety):** the rollup cap and the per-entity cap are wired to the
**same** `LOADER_MAX_GIB` env var, so a deliberate per-entity override silently raises the
rollup cap too — a real cost-blast-radius defect given the incident this phase exists to fix
(CR-01). Several secondary correctness/robustness issues follow.

## Critical Issues

### CR-01: `LOADER_MAX_GIB` override couples the per-entity cap and the rollup cap — a deliberate per-entity raise silently lifts the rollup ceiling

**File:** `scripts/loadUtahTransparency.js:60-66`
**Issue:**
```js
const MAX_BILLED_GIB = Number(process.env.LOADER_MAX_GIB) || 2;   // per-entity default 2
const ROLLUP_MAX_GIB  = Number(process.env.LOADER_MAX_GIB) || 64;  // rollup default 64
```
Both caps read the **same** env var. The documented workflow (`docs/utah-bigquery-access.md:102-103`)
explicitly tells the operator to set `LOADER_MAX_GIB=<n>` for "a deliberate one-off" per-entity
query — e.g. `LOADER_MAX_GIB=50`. If that operator then runs `--rollup --confirm` in the same
shell session, `ROLLUP_MAX_GIB` is now `50`, not the intended `64` — or worse, if they set a large
value to force a per-entity raw scan (`LOADER_MAX_GIB=2000`), the rollup cap becomes 2000 GiB and the
guardrail that is supposed to fail-closed at 64 GiB no longer does. The whole point of this phase is
to make it impossible to accidentally bill a large scan; coupling the two caps to one knob reintroduces
that exact footgun. This is the highest-leverage cost-safety defect in the new code.

Note: the only thing that still protects the rollup path here is the separate `fitsUnderQuota`
(`bytes <= 2**40`) check, but that ceiling is 1 TiB — 16x the intended 64 GiB rollup cap — so a coupled
override well above 64 GiB would pass the quota gate and bill far more than intended.

**Fix:** Give the rollup its own independent env var (and keep its default fixed regardless of the
per-entity override):
```js
const MAX_BILLED_GIB = Number(process.env.LOADER_MAX_GIB) || 2;
// Independent knob; rollup default stays 64 even when LOADER_MAX_GIB is set for a per-entity one-off.
const ROLLUP_MAX_GIB = Number(process.env.ROLLUP_MAX_GIB) || 64;
```
Update `docs/utah-bigquery-access.md` accordingly. Optionally hard-clamp the rollup cap
(`Math.min(ROLLUP_MAX_GIB, 64)`) so it can never be raised by env at all.

## Warnings

### WR-01: Rollup hardcodes `p_population: 0`, which can clobber the real populations already loaded for the 15 Utah entities

**File:** `scripts/loadUtahTransparency.js:675-677` (and the per-entity analog at `518-521`)
**Issue:** Every rollup group calls
```js
await supabase.rpc('treasury_ensure_municipality', {
  p_name: displayName, p_state: state, p_entity_type: group.entityType, p_population: 0,
});
```
The 15 target entities were loaded with real populations in Phases 68-71. The established pattern in
sibling loaders passes the actual value (`bulkLoadStateController.js:106` -> `p_population: population || 0`).
If `treasury_ensure_municipality` performs an UPDATE/UPSERT of `population` on an existing row (rather
than insert-only / COALESCE-on-existing), every rollup refresh will overwrite those populations with 0 —
silent data degradation on the exact entities this ETL is meant to maintain. The RPC body is not in the
repo so the behavior cannot be confirmed here; given the phase's "idempotent refresh / nothing degraded"
goal (`docs/utah-bigquery-access.md:97-98`), this needs verification.

**Fix:** Confirm the RPC's population semantics. If it can overwrite, fetch existing population first
(rollup already calls `findEntityMunicipality`, which selects `population`) and pass the existing value,
or pass `null` / omit so the RPC preserves the current value:
```js
const existingPop = existing?.population ?? 0;
await supabase.rpc('treasury_ensure_municipality', { ..., p_population: existingPop });
```

### WR-02: `treasury_sync_city_budget` deletes+replaces and leaves a stale `data_source` label — relabel from another source not detectable on re-run

**File:** `scripts/loadUtahTransparency.js:684-698`
**Issue:** Per project memory (`treasury_sync_city_budget is NOT source-safe`), the RPC DELETEs and
re-inserts categories/line-items for an existing `(muni, fy, dataset)` row and updates total/url/date
but does **not** update `data_source`. The rollup correctly guards with `findConflictingBudget` before
writing, so a *different-source* row is skipped. However, the never-overwrite guard only inspects rows
that already exist at scan time; the RPC itself remains non-source-safe. This is acceptable given the
pre-skip, but the guard and the write are not atomic — between `findConflictingBudget` (line 658) and the
`treasury_sync_city_budget` call (line 684) there is no transaction, so a concurrent different-source
write could be clobbered. Low likelihood for a manual single-operator ETL, but worth noting because the
RPC will happily overwrite and mislabel.

**Fix:** Document the assumption that the rollup is single-operator/manual (it already is in the runbook),
and consider making `treasury_sync_city_budget` itself enforce source-identity (update `data_source`, or
reject cross-source writes) so the invariant does not depend solely on the loader pre-check. At minimum,
ensure the RPC updates `data_source` to `Transparent Utah` on refresh so a same-source re-run cannot leave
a stale label.

### WR-03: `runGuardedQuery` cap-trip detection is regex-fragile — a differently-worded BigQuery error yields a misleading message

**File:** `scripts/loadUtahTransparency.js:404`
**Issue:**
```js
if (/bytes billed|maximum bytes/i.test(err && err.message)) {
```
The cap-exceeded path is recognized purely by matching the error string. BigQuery's
`maximumBytesBilled` rejection message wording is not contractual and can vary by client version/locale.
If it changes, the helpful "use --rollup / set LOADER_MAX_GIB" guidance is skipped and the raw error is
thrown. This is fail-safe for cost (the query is still rejected server-side without billing), so it is a
WARNING not a BLOCKER — but the operator loses the actionable message exactly when they most need it.
Also note `err && err.message` passed to `.test()` coerces a falsy err to the string `"false"`/`"null"`,
which is harmless but sloppy.

**Fix:** Prefer matching the structured error reason when available (BigQuery surfaces
`err.errors?.[0]?.reason === 'bytesBilledLimitExceeded'`) and fall back to the regex:
```js
const reason = err?.errors?.[0]?.reason;
if (reason === 'bytesBilledLimitExceeded' || /bytes billed|maximum bytes/i.test(err?.message ?? '')) {
```

### WR-04: Rollup cap (64 GiB) is below the quota ceiling (1 TiB) used by `fitsUnderQuota`, so a >64 GiB-but-<1 TiB scan passes the preview then fails the real scan

**File:** `scripts/loadUtahTransparency.js:437, 601, 614-618, 620-631`
**Issue:** `fitsUnderQuota` checks `bytes <= 2**40` (1 TiB). The real scan caps at `ROLLUP_MAX_BYTES_BILLED`
(~64 GiB). If the source table grows such that the dry-run reports, say, 80 GiB, the preview prints
`1 TiB/day quota: FITS` and `Rollup cap: 64 GiB (WOULD TRIP CAP)`, the `--confirm` branch passes the
`fitsUnderQuota` gate (line 614), then the actual `runGuardedQuery` fails on the 64 GiB cap (fail-closed,
good) — but only *after* the operator has committed, and the failure message points at the cost guard
rather than "raise the rollup cap deliberately." The two thresholds are inconsistent and the WOULD-TRIP-CAP
preview line is not enforced as a hard stop.

**Fix:** Gate the `--confirm` real scan on the cap as well as the quota:
```js
if (gib > ROLLUP_MAX_GIB) {
  console.error(`ERROR: estimated ${gib.toFixed(0)} GiB exceeds rollup cap ${ROLLUP_MAX_GIB} GiB — aborting.`);
  process.exit(1);
}
```
Place this check before the billed scan so the operator sees a clean abort instead of a post-confirm BQ error.

### WR-05: `groupRollupRows` FY filter excludes only the upper bound (`> 2025`) — rows below 2014 would slip through the in-memory guard

**File:** `scripts/loadUtahTransparency.js:194`
**Issue:**
```js
if (Number(row.fiscal_year) > 2025) continue;
```
The query WHERE is `BETWEEN 2014 AND 2025`, but the comment at lines 176-178 claims the in-memory pass
"guards again" defensively. It only guards the upper bound. A row with `fiscal_year < 2014` (e.g. a future
query change, a bad cast, or `NaN` from a non-numeric value — `Number('') === NaN`, and `NaN > 2025` is
`false`) would pass the guard and be grouped. The defensive intent is half-implemented; `NaN` years in
particular would create a group keyed `...|NaN|...`.

**Fix:** Mirror the query bounds and reject non-finite years:
```js
const fy = Number(row.fiscal_year);
if (!Number.isFinite(fy) || fy < 2014 || fy > 2025) continue;
```

## Info

### IN-01: `row_count` is recomputed by re-filtering `allRows` for every group — O(groups x rows) and duplicative

**File:** `scripts/loadUtahTransparency.js:690-694`
**Issue:** For each group, `p_row_count` re-scans the entire `allRows` array with `.filter(...).length`.
`groupRollupRows` already partitioned the rows per group (`group.rows`); the count is already known there.
(Performance is out of v1 scope, flagged as Info for maintainability — the count could diverge from the
grouped set if the keying logic ever differs from the filter predicate.)
**Fix:** Have `groupRollupRows` return `rowCount: group.rows.length` per group and use `group.rowCount`
directly, so the count and the tree always derive from the same partition.

### IN-02: `estimatedUSD` uses a hardcoded `$6.25/TiB` magic number

**File:** `scripts/loadUtahTransparency.js:436`
**Issue:** `(bytes / 2 ** 40) * 6.25` embeds the on-demand BigQuery price inline. If the price changes the
preview silently misreports cost.
**Fix:** Extract a named constant `const BQ_USD_PER_TIB = 6.25;` near the other cost constants with a
comment dating the price.

### IN-03: Dry-run job result accesses deeply-nested metadata without null-guards

**File:** `scripts/loadUtahTransparency.js:434`
**Issue:** `Number(job.metadata.statistics.totalBytesProcessed)` assumes the full path exists. If a future
client version returns a job without populated `statistics`, this throws a `TypeError` rather than a clear
"could not estimate bytes" message. Low risk (the BQ client reliably populates this for dry-runs).
**Fix:** Optional-chain and validate: `const raw = job?.metadata?.statistics?.totalBytesProcessed; if (raw == null) throw new Error('Dry-run returned no byte estimate');`

### IN-04: `parseArgs({ strict: false })` silently accepts typo'd flags

**File:** `scripts/loadUtahTransparency.js:559`
**Issue:** With `strict: false`, a mistyped flag such as `--confrim` is silently ignored rather than
erroring. For a cost-sensitive tool where `--confirm` is the billing gate, a typo'd confirm flag would
silently run the dry-run-only path (safe direction) — but a typo on other flags (`--rollupp`) would fall
through to per-entity mode and error on the missing `--entity`, which is confusing. Acceptable but worth a
note.
**Fix:** Consider `strict: true` for the rollup flags, or at least validate that unknown positionals/flags
are absent before acting.

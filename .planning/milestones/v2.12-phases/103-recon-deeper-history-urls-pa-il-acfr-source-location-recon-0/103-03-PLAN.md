# Plan 103-03 — Loader-reuse + NASBO-replace plan + 103-RECON.md assembly

**Mode:** standard
**Goal:** Turn the deepening recon (103-01) and the PA/IL source location (103-02) into the actionable plan Phases 104–105 execute: which pilot loader `SOURCES` maps get the new older-FY URLs, which `process*Acfr.js` template fits PA + IL, and exactly how ACFR rows replace NASBO operating rows idempotently — then consolidate everything into one decision-ready `103-RECON.md`. Documentation only; no DB writes; $0. Covers RECON-05 (the replace-enabling plan) and the phase's third success criterion.

<threat_model>
**T-103-03 — A loose loader mapping or vague replace rule lets Phase 104 disturb existing pilot rows, or Phase 105 double-count / strand a PA/IL state-FY.**
- *Surface:* a planning document mapping pilots→SOURCES-map edits and PA/IL→loaders, and specifying the replace semantics.
- *Threats:* (a) a SOURCES-map extension plan vague enough that Phase 104 re-writes or overwrites the existing FY rows it should leave alone; (b) recommending a PA/IL template whose layout doesn't actually match, forcing the executor to improvise; (c) under-specifying "replace" so PA/IL NASBO rows survive alongside ACFR rows (two bases for one state-FY); (d) forgetting un-upgraded NASBO states must remain untouched; (e) recommending a replace for a state whose clean window misses FY2023/FY2024 (the D-06 strand).
- *Mitigations:* the SOURCES-map plan states "add only the new older-FY keys; existing FY entries + their transcribed blocks are untouched — idempotent re-run = 0 writes on existing rows"; each PA/IL mapping cites the specific layout features that match (revenue-by-source columns, spend-by-function rows) from 103-PA-IL-SOURCES.md; the replace rule is stated as delete-NASBO-state-FY-then-insert-ACFR, one basis per state-FY, idempotent, scoped to PA/IL only, loadStateGF.mjs untouched for all other states; the D-06 recent-window verdict gates each replace recommendation.
- *Block on:* high.
</threat_model>

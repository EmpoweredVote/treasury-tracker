# Plan 58-01 — LA County city history backfill (FY2003–2024)

**Mode:** standard
**Goal:** Execute **Step 1** of `docs/socal-county-onboarding.md` for Los Angeles County: a full **FY2003–2024** reload of operating + revenue for every SCO-sourced LA County city via the existing `scripts/bulkLoadStateController.js --county "Los Angeles"`. This (a) adds the missing FY2003–2016 history, (b) **repairs the NULL `source_url`** on the existing FY2017–2024 rows by re-syncing them with the durable `/d/` page URL, and (c) layers SCO history beneath the thin/non-comparable custom cities (Long Beach, West Hollywood) without overwriting their custom years. Satisfies HIST-01.

**Why a full reload is safe (verified, D-01):** `bulkLoadStateController.js:41` writes `data_source = "CA State Controller - ${label}"` ("Expenditures"/"Revenues"). The existing LA County city rows carry *exactly* those labels, and `findConflictingBudget` (:87-101) preserves a row only when its `data_source !== ` the loader's own label. Same label ⇒ returns null ⇒ "safe to refresh" ⇒ re-syncs via `treasury_sync_city_budget` with `p_source_url = ds.pageUrl`. So re-running FY2017–2024 repairs their source_url rather than skipping them. **No separate source-repair step is needed.**

**Never-overwrite set (verified, D-03):** exactly 3 cities have a non-SCO `data_source` and are therefore preserved per (fiscal_year, dataset): **Los Angeles** (data.lacity.org / LA City Budget/Checkbook/Payroll/Revenue, FY2017–2026 — stays fully custom, D-05), **Long Beach** (custom GF FY2025–26 only), **West Hollywood** (Demand Register FY2018–26). For Long Beach + West Hollywood the SCO years with no existing row load cleanly beneath their custom years (D-04).

**Load shape:** a single 22-year × all-cities run risks the 600s command timeout. So: dry-run → capture custom-city baseline → **canary FY2024** (a year already present — proves the re-sync repairs source_url and skips custom) → verify → **backfill FY2003–2023 in small year-chunks** (≤3 years/submit; widen/narrow per observed runtime). Writes are idempotent on (municipality_id, fiscal_year, dataset_type), so any chunk is safe to re-run.

<threat_model>
**T-58-01 — A full-range reload clobbers a custom-source city's data, writes unsourced rows, or silently skips the FY2017–2024 source-repair.**
- *Surface:* `bulkLoadStateController.js` writes budget rows for every SCO city in the county via the service-role key. A label mismatch could turn the intended re-sync of FY2017–2024 into a collision-skip (leaving source_url NULL), or — worse — a custom city could be overwritten if its label ever matched the loader's.
- *Threats:* (1) silent loss of LA / Long Beach / West Hollywood custom data; (2) FY2017–2024 rows left with NULL source_url (always-sourced violation) if they were unexpectedly skipped; (3) a 0 population breaking per-capita; (4) a partial/timed-out backfill that still "looks" done.
- *Mitigations:* (1) **baseline probe** of the 3 custom cities' rows (data_source + fy set + totals) captured BEFORE any write and re-checked AFTER (task 02 + 05); (2) **canary FY2024** verifies the existing rows were re-synced (source_url now `/d/…`) and the custom cities were SKIP-logged — before any backfill (task 03 gates task 04); (3) population backfill is write-only on 0/NULL (never lowers a non-zero pop); (4) every write passes `p_source_url` (durable `/d/<id>`) + `p_source_date`; (5) idempotent chunks; final probe confirms FY2003 reach + source_url coverage + custom-untouched.
- *Block on:* high. Do not run the FY2003–2023 backfill (task 04) until the canary (task 03) proves source_url repaired on a re-synced year AND the 3 custom cities SKIP-logged/unchanged.
</threat_model>

# Phase 71.1: Utah Single-Scan Rollup ETL (BigQuery cost fix) - Context

**Gathered:** 2026-06-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the loader's per-`(entity, fiscal_year, type)` **live** BigQuery query pattern — which full-table-scans the unpartitioned source `ut-sao-transparency-prod.transaction.transaction` (~35–47 GiB per query regardless of the `WHERE` filter) and ran up ~21 TiB / ~$132 in one day (2026-06-19) — with a **single rollup-scan ETL**. One BigQuery query pulls all 15 Utah entities × all fiscal years × all types in one pass; the rows are grouped in memory into the existing trees and written to Supabase via the existing RPC. BigQuery becomes a **periodic source, run manually**, exactly like every other source (CA is pulled once from the SCO REST API into Supabase, never queried live).

**In scope:** a `--rollup` mode on `scripts/loadUtahTransparency.js`; one unified aggregate query; dry-run cost preview + `--confirm` gate; idempotent refresh into Supabase reusing the existing write path; adding `UETL-01` to REQUIREMENTS.md.

**Out of scope (deferred):** any scheduler/cron (refresh is manual-only this phase); migrating to a dedicated service account (later follow-up — needs the Transparent Utah grant extended); re-partitioning or copying the source table; any app/frontend change (the app already reads Supabase, never BigQuery).

</domain>

<decisions>
## Implementation Decisions

### Script shape
- **D-71.1-01:** Implement as a `--rollup` mode **inside `scripts/loadUtahTransparency.js`**, not a new sibling script or a shared-core refactor. Reuse the existing internals directly — `buildTree` (EX/RV 3-level), `buildSalaryTree` (PY 2-level), `importEntityData`, the never-overwrite guard (`findConflictingBudget`/`neverOverwriteDecision`), `toDisplayName`, and `runGuardedQuery`. New code is limited to: one fetch function (the single unified query) + a loop that groups the returned rows by `(entity_name, fiscal_year, type)` and calls the existing per-group import. Rationale: least churn, no new exports, single file to maintain — this is remediation, not new architecture.

### Query strategy
- **D-71.1-02:** **One unified scan**, no `WHERE` filter:
  `SELECT entity_name, fiscal_year, type, COALESCE(fund1,'Unknown') fund1, COALESCE(org1,'General') org1, COALESCE(cat1,'General') cat1, SUM(amount) amount FROM \`ut-sao-transparency-prod.transaction.transaction\` GROUP BY entity_name, fiscal_year, type, fund1, org1, cat1`.
  Covers all 15 entities × all FYs × `EX`/`RV`/`PY` in ~1 scan (~$0.29). 
- **D-71.1-02a (names-free preserved):** `fund1`/`org1`/`cat1` are NOT PII. No PII column (vendor_name, dba_name, vendor_code, title, hourly_rate, gender, account_number, contract_name, contract_number, description, ref_id) is ever projected. For `type='PY'` rows, **drop `fund1` and re-sum across funds in memory** before `buildSalaryTree`, so the stored salaries tree stays the 2-level Department→Wages/Benefits shape (D-71-02) — identical to what Phase 71 stored. EX/RV rows keep `fund1` for the 3-level tree (D-69-01).

### Scan safety / UX
- **D-71.1-03:** The rollup path **dry-runs first** (BigQuery `dryRun: true` — free, returns estimated bytes without scanning), prints estimated **GiB + $ + whether it fits under the 1 TiB/day quota**, then requires an explicit **`--confirm`** flag to perform the real scan + writes. Default (no `--confirm`) = preview only, zero scan-billing, zero writes.
- **D-71.1-03a:** The real rollup scan uses a **built-in higher `maximumBytesBilled` cap (~64 GiB)** on the rollup path so it "just works" without an env override. The existing per-`(entity,FY,type)` path keeps the **2 GiB default cap** from commit `8e59851` (it stays effectively safed-off). `LOADER_MAX_GIB` remains the override for either path.

### Refresh semantics
- **D-71.1-04:** Re-running is an **idempotent upsert of our own Transparent Utah rows** — overwrite the existing `(municipality, fiscal_year, dataset_type)` row with fresh totals/trees via the RPC. The never-overwrite guard still **SKIPS any different-source row** untouched (SC#4 posture from Phase 71). An `(entity, fiscal_year, type)` absent from the new scan → **leave the prior stored row in place (never delete)** and log it as a coverage note. Never silently drop loaded data; never prune.

### Claude's Discretion
- Exact CLI surface of `--rollup` (whether it ignores `--entity`/`--fy`/`--type` or treats them as optional filters), log formatting, and the in-memory grouping data structure are left to the planner/executor, provided the decisions above hold.
- Whether to add a lightweight post-load reconciliation (compare rollup-produced row counts/totals against the Phase-71 per-entity state, since they should match) — nice-to-have; planner's call.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `buildTree(rows, TREE_OPTS)` + `buildSalaryTree(rows)` — produce the exact stored tree shapes; the rollup feeds grouped rows straight in (PY rows get `fund1` collapsed first).
- `importEntityData(...)` — the write path (treasury_ensure_municipality → treasury_sync_city_budget with source_url/source_date) + never-overwrite guard + `toDisplayName`. Reused verbatim per group.
- `runGuardedQuery(opts)` — injects `maximumBytesBilled`; the rollup raises the cap (~64 GiB) for its one intentional scan.
- `typeToDataset` / `amt` / `DATA_SOURCE_NAME` — already exported and unit-tested.

### Established Patterns
- CA loader (`bulkLoadStateController.js`) = one multi-entity fetch → group → per-entity import. This is the template; Utah differs only in fetch layer (one BigQuery scan vs Socrata paging) and the extra grouping keys.
- Cost guardrail (commit `8e59851`): per-query `maximumBytesBilled` default 2 GiB; `LOADER_MAX_GIB` override. The rollup path layers a higher built-in cap on top.

### Integration Points
- Writes land in Supabase `treasury.budgets` (+ line items) via `treasury_sync_city_budget`; the app renders from there with no change.
- BigQuery is reached via ADC (live as of 2026-06-19); the 1 TiB/day project quota is intentional and must NOT be raised — the single rollup scan (~47 GiB) fits under it after the daily reset.

</code_context>

- The user's preferred end state (verbatim intent): "Treat BigQuery as a once-in-a-while SOURCE, not a live backend." Pull the pre-aggregated rollup, repoint nothing (app already on Supabase), refresh manually.

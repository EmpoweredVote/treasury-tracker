# Plan 98-03 — Loader-reuse + NASBO-replace plan + RECON.md assembly

**Mode:** standard
**Goal:** Turn the located/extracted ACFR sources (98-02) and the CA recommendation (98-01) into the actionable plan Phases 99–100 execute: which existing `process*Acfr.js` template fits each state, and exactly how ACFR rows replace NASBO operating rows idempotently. Consolidate everything into one decision-ready `98-RECON.md`. Documentation only. Covers the phase's third success criterion.

<threat_model>
**T-98-03 — A loose loader mapping or vague replace rule lets Phase 99 double-count a state-FY (NASBO + ACFR both present) or silently drop revenue.**
- *Surface:* a planning document mapping states→loaders and specifying the replace semantics.
- *Threats:* (a) recommending a template whose layout doesn't actually match the state's GF statement, forcing the executor to improvise; (b) under-specifying "replace" so NASBO rows survive alongside ACFR rows (two baseses for one state-FY); (c) forgetting that un-upgraded NASBO states must remain untouched.
- *Mitigations:* each mapping cites the specific layout features that match (revenue-by-source columns, spend-by-function rows) drawn from 98-02's extracted text; the replace rule is stated as "delete this state's NASBO (state-FY) operating rows, then insert ACFR rows — one basis per state-FY — idempotent re-run = 0 writes; loadStateGF.mjs untouched for all other states"; explicitly scope the replace to the four upgraded states only.
- *Block on:* high.
</threat_model>

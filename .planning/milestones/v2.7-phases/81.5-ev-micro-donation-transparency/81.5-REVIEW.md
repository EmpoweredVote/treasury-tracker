# Phase 81.5: Code Review Report

**Reviewed:** 2026-06-23T00:00:00Z
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

Phase 81.5 adds (1) anonymized recurring-supporter aggregation to `scripts/loadEVDonations.js`
with a compact JSON carrier persisted onto the `Donations` budget_category row, (2) a
`MicroDonationCallout.tsx` React component that reads those aggregates and renders an honest
"how we stay free" stat, and (3) the import + nonprofit-gated mount in `App.tsx`.

**Privacy assessment (heavily weighted):** PASS at the design level. The aggregate pipeline
(`giveButterRecurringDonors`, `patreonDistinctPatrons`, `computeRecurringAggregates`) consumes
PII columns (Contact ID, Contact Email, Member user ID) only as in-memory dedup keys and never
returns or persists them. The persisted payload (`recurring_supporters`, `typical_monthly`,
`buckets`, `as_of_fy`) contains only counts and a median, and the test suite includes an explicit
no-PII-keys assertion. No donor names/emails/addresses reach the DB carrier or the frontend.
The carrier reuses the existing `description`/`item_count` API fields, so no schema change. This
is sound — but see WR-01 for a latent privacy/honesty edge with low-cardinality buckets, and
WR-02 for a numeric-parse inconsistency that can silently corrupt the displayed median.

**Honesty assessment (heavily weighted):** Mostly PASS. The UI renders only persisted aggregates
and degrades gracefully to a static headline when aggregates are absent or `supporterCount === 0`.
The Benevity = 1 rule is implemented and tested. Two honesty gaps worth flagging: a supporter-count
vs bucket-count mismatch (WR-03) and a stale-`as_of_fy` blind spot in the UI (WR-04).

**Correctness:** Dedup logic and the JSON-carrier parse are correct and defensively coded
(try/catch + type guards in `parseEvMicro`). One numeric-parse divergence (WR-02) and one
`asOf` horizon edge (WR-05) are the substantive correctness risks.

No BLOCKER-class defects (no injection, no PII leak, no crash-on-load) were found.

## Warnings

### WR-01: Low-cardinality size buckets can be quasi-identifying for a tiny donor pool

**File:** `scripts/loadEVDonations.js:240-241`, surfaced via `description` carrier
**Issue:** With only ~8 GB+Patreon supporters in the real FY2026 data (per the reconciliation
test, buckets = `{b5to9:3, b10to24:2, gte50:3}`), the per-bucket counts are persisted and shipped
to every client through `category.description`. For an organization this small, a single-occupant
bucket (e.g. `gte50:1`) combined with the public gross-by-source figures already in the Donations
tree can narrow a donor's monthly amount to a near-unique value. This is not a name/email leak, but
for EV's own micro-donation story it weakens the "anonymized aggregate" guarantee the phase set out
to provide, and the buckets are not currently consumed by the UI at all (only `recurring_supporters`
and `typical_monthly` are rendered).
**Fix:** Either suppress/round buckets when any non-zero bucket has a count below a small-cell
threshold (e.g. drop buckets entirely when `recurring_supporters < 10`), or stop persisting `buckets`
in the carrier until a consumer needs them:
```js
const SMALL_CELL = 5;
const buckets = recurring_supporters >= 10 ? rawBuckets : undefined; // omit for tiny pools
```

### WR-02: Patreon median uses raw `parseFloat`, not the `money()` parser — silently zeroes formatted amounts

**File:** `scripts/loadEVDonations.js:175`
**Issue:** `patreonDistinctPatrons` reads the per-patron amount with
`parseFloat(r['Member charge amount']) || 0`, while every other money field in this loader goes
through `money()` (which strips `$`, commas, parens). If Patreon's detailed-earnings export ever
emits `"$5.00"` or `"1,000.00"` (locale/format drift is common across platform export versions),
`parseFloat('$5.00')` is `NaN → 0`. Those patrons then contribute `$0` to the median and land in the
`lt5` bucket — corrupting the "typical $X/month" honesty number with no error. The monthly Patreon
parser (`parsePatreon`, line 109) correctly uses `money()`, so the two code paths disagree on the
same source family.
**Fix:** Use the shared parser for consistency and robustness:
```js
if (!seen.has(id)) seen.set(id, money(r['Member charge amount']));
```

### WR-03: Displayed supporter count includes Benevity but the median/buckets exclude it — internally inconsistent

**File:** `scripts/loadEVDonations.js:231-241`, rendered at `MicroDonationCallout.tsx:91-94`
**Issue:** `recurring_supporters` = GB + Patreon + 1 (Benevity), but `allAmounts` (which drives both
`typical_monthly` and `buckets`) deliberately excludes the Benevity supporter. The UI then renders
"9 people give — typically around $10/month", where the 9 includes a supporter who is not part of the
$10 median population. The bucket counts likewise sum to 8, not 9. This is defensible (company-match
is atypical), but it is an undocumented inconsistency in the user-facing claim and a latent honesty
snag: "N people give ~$X/month" implies all N are described by $X.
**Fix:** Make the exclusion explicit in the carrier and/or copy, e.g. persist a separate
`median_population` count, or phrase the UI as "most give around $X/month" rather than implying the
full headcount. At minimum add a code comment at the render site noting the count/median population
differ by the Benevity supporter.

### WR-04: UI never surfaces `as_of_fy`, so a stale loader run shows current-looking numbers

**File:** `src/components/dashboard/MicroDonationCallout.tsx:74-97`
**Issue:** `parseEvMicro` reads `as_of_fy` (and the interface requires it) but the component never
renders or validates it. If the loader was last run for FY2025 and the user is viewing the FY2026
dashboard, the callout will confidently display the FY2025 supporter count with no temporal qualifier
— an honesty gap, since the headline ("currently sustained by...") implies present-tense data. There
is also no guard that `as_of_fy` matches the selected fiscal year in `App.tsx`.
**Fix:** Either render the period ("9 people give … (FY{micro.as_of_fy})") or, in `App.tsx`, only
mount the callout when `donationsCat`'s `as_of_fy` matches the selected year; fall back to the static
headline otherwise.

### WR-05: `asOf` export horizon is computed over all fiscal years, can over-suppress webhook delta

**File:** `scripts/loadEVDonations.js:95-96`
**Issue:** `parseGiveButter` sets `asOf` to the max `Transaction Date (UTC)` across *all* succeeded,
non-refunded rows regardless of FY (the FY filter at line 97 is applied only after the `asOf` update).
If the export contains any succeeded row dated after the target FY (e.g. a re-export pulled in early
the next calendar year, or a future-dated row), `asOf` jumps past the FY and `giveButterDedup`
classifies legitimately-new webhook rows as `superseded`, dropping them from the live delta and
undercounting revenue. The intent comment ("over all succeeded rows") suggests this is deliberate, but
combined with the per-FY revenue write it is a quiet correctness risk.
**Fix:** Constrain the horizon to the target FY, or clamp it:
```js
if (isoYear(r['Transaction Date (UTC)']) !== fy) continue; // move FY filter first
const d = isoDate(r['Transaction Date (UTC)']);
if (d && (!asOf || d > asOf)) asOf = d;
```

## Info

### IN-01: Component doc comment references `category.items` carrier that the code never reads

**File:** `src/components/dashboard/MicroDonationCallout.tsx:10-12`
**Issue:** The JSDoc says `category.items = distinct active recurring-supporter count (item_count in DB)`
and frames it as a data source, but the render path relies solely on `parseEvMicro(description)` —
`category.items` is never accessed. The loader does persist `item_count` (line 477), but it is dead
as far as this component is concerned. Misleading for the next maintainer.
**Fix:** Either drop the `items` line from the doc, or use `category.items` as a sanity cross-check
against `micro.recurring_supporters` and log/ignore on mismatch.

### IN-02: `gb_amount` / `donations_amount` helpers are trivial indirection

**File:** `scripts/loadEVDonations.js:429-430`
**Issue:** `const gb_amount = c => Number(c.amount || 0)` and the identical `donations_amount` add no
behavior over an inline `Number(x.amount || 0)` and read as if they fetch fresh DB state (the comment
says "read the just-fetched amounts") when they only coerce the already-in-memory value. Minor
clarity cost.
**Fix:** Inline the coercion or rename to `toAmount` and use one helper for both.

### IN-03: Reconciliation test embeds hard-coded production export filename and Windows path hack

**File:** `scripts/loadEVDonations.test.mjs:274-275`
**Issue:** The live-reconciliation gate hard-codes `givebutter_transactions-2026-06-21-1895409277.csv`
and reimplements CSV parsing inline (lines 278-298) rather than importing `readCsvRows`. The pinned
filename means a re-export breaks the test by path-not-found rather than by a clean assertion failure,
and the duplicated parser can drift from the production one. The `.replace(/^\/([A-Z]:\/)/i, ...)`
path fix is also a platform-specific hack.
**Fix:** Import `readCsvRows` from the module under test, and glob the export by the same regex the
loader uses (`/givebutter.*transactions.*\.csv$/i`) instead of pinning the exact filename.

### IN-04: `typical_monthly != null` guard is redundant after the `> 0` check

**File:** `src/components/dashboard/MicroDonationCallout.tsx:92-94`
**Issue:** `micro!.typical_monthly != null && micro!.typical_monthly > 0` — the `> 0` comparison
already excludes `null`/`undefined`/`NaN` (all yield false), and `parseEvMicro` already type-guards
`typical_monthly` as a `number`. The null check is dead. Also note the non-null assertions (`micro!`)
are safe here only because `hasAggregates` implies `micro !== null`, but that coupling is implicit.
**Fix:** Simplify to `micro!.typical_monthly > 0`, and consider destructuring `micro` after the
`hasAggregates` guard to drop the `!` assertions.

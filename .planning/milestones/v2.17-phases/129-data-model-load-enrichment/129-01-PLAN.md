# Plan 129-01 — Tucson city + Pima County data model

**Mode:** standard
**Goal:** Stand up the navigation nodes so Tucson has a home before any budget loads. Seed the Tucson city entity and a Pima County navigation node under the existing Arizona state node, and link Tucson to Pima via `municipalities.county_id`. After this plan the `US → Arizona → Pima County → Tucson` breadcrumb and the Cities-in-County panel have the data they need to render (the render itself is confirmed in Phase 130 UAT).

This plan writes **one idempotent seeder** (`scripts/seedTucsonArizona.js`) covering both TUC-03 and TUC-04. It does **no** budget load, no enrichment, no schema change, and creates **no** `data_source` rows (those are owned by `processTucson.js`, Plan 129-02).

<threat_model>
**T-129-01 — Privileged writes to the shared production `municipalities` table with a service-role key.**
- *Surface:* the seeder authenticates with `SUPABASE_SERVICE_KEY` and inserts/updates rows in `treasury.municipalities`.
- *Threats:* (a) a non-idempotent insert creating a duplicate Tucson or duplicate Pima County on re-run; (b) silently repointing a city that is already linked to a different county; (c) fabricating a population figure.
- *Mitigations:* select-by-(name,state[,entity_type]) → insert-or-update (never blind insert); set `county_id` only when NULL or already Pima (the `seedCountyLinks.js` guard); pin population from the 2024 Census vintage (no invented number). Reads before writes; no shell interpolation.
- *Block on:* high (a duplicate node or a mis-link corrupts navigation for a shared production app).
</threat_model>

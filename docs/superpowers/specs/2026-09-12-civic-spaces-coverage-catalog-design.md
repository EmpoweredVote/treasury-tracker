# Civic Spaces Asks 1 + 2 — a geoid column and a published coverage catalog

**Date:** 2026-09-12
**Status:** design approved, ready for planning
**Origin:** `TT-TEAM-NOTE-coverage-catalog-2026-09-08.md` (PR #157, branch
`docs/civic-spaces-coverage-note` — read with
`git show ccb8642:TT-TEAM-NOTE-coverage-catalog-2026-09-08.md`)
**Consumer-side design:** `C:/Civic Spaces/.planning/phases/15-tool-deep-links/15-DESIGN.md`

Ask 3 of that note is already done — PR #158 / `ca0f331`, the Bloomington
fallback. This spec covers Asks 1 and 2, which were deferred on 2026-09-08.

---

## 1. What is being built, and why

Civic Spaces places each member into civic slices and wants a sidebar row that
opens **that member's own government's budget in Treasury Tracker**. It cannot
build one today: Civic Spaces knows a jurisdiction only as a **Census FIPS
geoid**, and TT addresses entities only by a **name-derived slug**. There is no
key the two apps share.

So:

- **Ask 1** — put a `geoid` on TT entities.
- **Ask 2** — publish a catalog keyed by geoid, carrying the slug, mirroring the
  shape TT *already consumes* from Essentials in `src/utils/essentialsCoverage.ts`.

TT is the publisher in exactly the way Essentials already is. A consumer points
one matcher at either catalog.

### The consumer's failure mode is safe by design

Civic Spaces' rule is **no match, no row**. A gap in TT's coverage costs them a
sidebar row; it never produces a wrong link. This matters for every scoping
decision below: *under-claiming is cheap, over-claiming is not.*

## 2. Decisions taken (2026-09-12, Chris)

| # | Decision | Chosen |
|---|---|---|
| D-1 | Backfill scope | **All tiers, all states** — state, county, place tier, and township/MCD. Null for anything that will not resolve cleanly. |
| D-2 | Where the catalog is served | **An endpoint on `ev-accounts-api`**, not a static file in `public/`. |
| D-3 | Payload size | **One URL with route-scoped gzip.** Not split by tier. |

### Why D-2, recorded because the note could not know it

**TT's build has no database access.** The frontend reads everything through
`/api/*` → `ev-accounts-api.onrender.com`; there is no `VITE_SUPABASE*` anywhere
in `src/`. A file in `public/` therefore cannot be built from the DB at deploy
time — it would have to be generated by a script and committed, making
`generatedAt` mean *last commit*, not *last deploy*. Separately, `render.yaml`
defines only the enrichment cron, so TT's static site is configured in the Render
dashboard and a CORS header there is a manual, unversioned change.

The API already holds the DB connection that serves `/treasury/cities`, sets CORS
in code, and is always fresh.

### Why D-3

Measured, not estimated: 7,395 cities + 699 counties in the requested shape is
**~810 kB uncompressed**, past the ~500 kB line the note draws. The API has **no
compression middleware**, so that is the real wire size. Route-scoped
`compression()` puts it near 100–130 kB while keeping one URL and their preferred
shape. Enabling gzip API-wide would also shrink the 12.3 MB `/treasury/cities`
list every TT page load fetches — a bigger win, and deliberately left as its own
separate decision rather than smuggled in here.

## 3. Feasibility — measured, not projected

The note assumed a Census API crawl and warned that townships might be
intractable. Both assumptions turned out to be wrong, in TT's favour.

`scripts/lib/censusPep.mjs` already parses the Census PEP bulk files, which are
free, need no key, and are already in TT's toolchain. `sub-est2024_<ss>.csv`
carries `SUMLEV,STATE,COUNTY,PLACE,COUSUB,...` — every key needed:

| tier | SUMLEV | geoid | length |
|---|---|---|---|
| state | — (static table) | `STATE` | 2 |
| county | 050 (`co-est2024-alldata.csv`) | `STATE+COUNTY` | 5 |
| place tier | 162 | `STATE+PLACE` | 7 |
| township / MCD | **061** | `STATE+COUNTY+COUSUB` | 10 |

`SUMLEV.minorCivilDivision` is already defined in that module.

Two states were measured end to end with throwaway probes:

| state | entities | resolved | ambiguous | wrong |
|---|---|---|---|---|
| Indiana | 659 | 651 (98.8%) | 0 | 0 |
| Michigan | 1,856 | **1,856 (100%)** | 0 | 0 |

Michigan includes all **1,240 townships** — the case the note flagged as the
likely blocker. Indiana's 7 misses are abbreviation variants (`Mt. Ayr` vs
Census `Mount Ayr town`; `Parker` vs `Parker City town`).

### ⚠⚠ The finding that makes the township tier work

**The Census designator must be REQUIRED, not stripped — the inverse of what the
note assumed.**

In an MCD state an incorporated **city is also a county subdivision**, so
`sub-est2024_26.csv` carries both `Adrian city` and `Adrian township` as
SUMLEV-061 rows in Lenawee County. `placeMatchKey` exists to strip
`city|town|village|borough|municipality|CDP` in order to build a *fuzzy
candidate*; applied to MCD rows it collapses those two to the same key. That
produced **105 false ambiguities in Michigan alone**, every one of them a chance
to attach a city's geoid to a township.

Restricting township matching to rows that actually end in
`township`/`charter township` took Michigan from 105 ambiguous to **0**.

This is the same shape as the note's own warning ("a township is not a place"),
one level deeper: *within* the MCD universe, a city is also an MCD.

## 4. Part 1 — the `geoid` column and its backfill

### 4.1 Schema

```sql
ALTER TABLE treasury.municipalities ADD COLUMN geoid text;
ALTER TABLE treasury.municipalities ADD COLUMN geoid_basis text;
```

- **`text`, not a number.** Leading zeros are meaningful — `01073` is Jefferson
  County, AL. An integer column eats them silently.
- **Length constrained per tier** (2 / 5 / 7 / 10 as in §3), enforced by a CHECK
  keyed on `entity_type`, so a wrong-length value cannot be stored at all.
- **`geoid_basis`** records how the value was derived —
  `static-state-fips`, `census-pep-050-exact`, `census-pep-162-exact`,
  `census-pep-061-county-scoped`. Without it a later reader cannot distinguish a
  verified match from a guess. Same reason `basis` and `audit_grade` exist on
  budgets, and the reason the Marion County finding stayed recoverable.
- **Nullable, with NO default.** A `NOT NULL DEFAULT` on a column meaning "we know
  this" is precisely the `fiscal_year_start_month` defect
  — the one that lied on ~18,700 rows: it would assert a geoid TT never derived,
  on every row, and nothing would fail.

The migration follows house style — a self-verifying `DO` block that
`RAISE EXCEPTION`s on failure. Applied via `mcp__supabase-local__apply_migration`
and committed under `supabase/migrations/`.

### 4.2 The backfill script

`scripts/backfillGeoids.mjs`, reading the Census PEP bulk CSVs. No API, no key,
**$0** — well under the $5 AI/API spend threshold.

Three rules, each earned from the probes rather than assumed:

1. **Require the designator; never strip it.** Township matching accepts only
   SUMLEV-061 rows ending in `township`/`charter township`. (§3.)
2. **Scope MCDs by county, taken from the stored name.** MI stores
   `"Acme Township, Grand Traverse County"`; the county half resolves to a
   `COUNTY` FIPS and scopes the lookup. This is what makes *117 township names
   naming 302 townships* (the MI F-65 sweep) unambiguous.
3. **Ambiguity writes a null, and logs.** More than one candidate geoid ⇒ write
   nothing. A miss costs a sidebar row; a wrong geoid points a reader at another
   government's budget — the reason Ask 3 existed at all.

`exactMatchKey` is never the sole discriminator. It is the space-deleting key
behind the open `buildFlStatewideEntities.mjs` collision — `elizabethtown` and
`elizabeth town` collapse identically under it. Here it is always paired with a
county scope or a required designator, so it cannot decide a match alone. **This
does not fix that bug; it declines to build on it.** Tracked separately.

Indiana's 7 abbreviation misses stay **null** in the first pass. A curated alias
table is a cheap follow-up once the true national miss rate is visible; guessing
now would be inventing coverage.

## 5. Part 2 — the `/coverage` endpoint

### 5.1 Route and mounting

A dedicated router, `backend/src/routes/publicCoverage.ts` in the **EV-Accounts**
repo, serving `GET /api/treasury/coverage`.

It is a separate file because of **where it must be mounted**, which is the one
genuinely tricky part of this design:

```ts
app.use(helmet());
app.use('/api/treasury/coverage', publicCoverageRouter);  // ← BEFORE the credentialed allowlist
app.use(cookieParser());
app.use(cors({ /* exact-match allowlist, credentials: true */ }));
```

⚠⚠ The global CORS policy sets `Access-Control-Allow-Credentials: true`. **A
browser rejects that in combination with `Access-Control-Allow-Origin: *`.** A
route-level `cors({ origin: '*' })` layered *after* the global middleware
therefore yields a response that fails in exactly the cross-origin consumers it
exists to serve, while passing every server-side test that does not run a
browser. Mounting ahead of the global middleware means the public endpoint never
acquires the credentialed header at all — and it needs neither cookies nor a body
parser, being an unauthenticated GET.

That ordering is load-bearing and non-obvious. It carries a comment saying so and
a test asserting `Access-Control-Allow-Credentials` is **absent**.

The router applies `cors({ origin: '*' })`, `compression()`, and
`Cache-Control: public, max-age=3600`.

### 5.2 Response shape

Exactly what `src/utils/essentialsCoverage.ts` already consumes, plus `slug`:

```json
{
  "generatedAt": "2026-09-12T00:00:00.000Z",
  "cities":   [{ "label": "Bloomington", "geoids": ["1805860"], "state": "IN", "slug": "bloomington-in" }],
  "counties": [{ "label": "Monroe County", "geoids": ["18105"], "state": "IN", "slug": "monroe-county-in" }],
  "states":   [{ "label": "Indiana", "abbrev": "IN", "slug": "indiana-in" }],
  "federal":  { "label": "United States", "slug": "united-states-us" }
}
```

- `geoids` stays a **single-element array**. TT has one geoid per entity, but
  matching the existing shape is the whole point — one matcher, either catalog.
- **Entities with a null geoid are omitted**, never `geoids: []`. Absent means
  "we cannot key this"; an empty array invites label-matching.
- **Only entities with at least one budget dataset.** 8,146 of 8,184 rows
  qualify; the catalog carries 8,145 of them, the `nonprofit` row (Empowered
  Vote) being out of scope. This filter removes little, but a row whose budget
  nobody can read must not be advertised as coverage.
- `states` (50) and `federal` always appear.
- **The federal slug is `united-states-us`** — the row is `name: "United States"`,
  `state: "US"`. This answers the question the note left open.
- Built by `getCoverageCatalog()` in `backend/src/lib/treasuryService.ts` via
  `pool.query` (the treasury schema is not PostgREST-exposed), memoised ~15
  minutes so an 810 kB serialisation is not rebuilt per request.

### 5.3 Slug uniqueness

Verified across all 8,184 rows: **8,183 distinct slugs**. The single collision is
`marine-on-saint-croix-mn` (two MN `city` rows). `resolveEntityParam` returns the
first match, so one of those two is unreachable by deep link. It is pre-existing,
unrelated to this work, and noted here because the verifier (§6) will flag it.

## 6. Testing and verification

The regression test that matters most is **`Adrian city` vs `Adrian township` in
Lenawee County** — the 105-way ambiguity a stripped designator reintroduces
silently. It goes in as a fixture, not a comment.

- **Matcher unit tests** (TT repo): designator-required; county-scoped MCD;
  ambiguity ⇒ null; leading-zero preservation.
- **Endpoint tests** (EV-Accounts repo): omits null-geoid entities; omits
  entities with no budget; `Access-Control-Allow-Origin: *` present and
  `Access-Control-Allow-Credentials` **absent**; gzipped body under 500 kB.
- **`scripts/verifyCoverageCatalog.mjs`** (TT repo): fetches the live endpoint and
  asserts every slug resolves through `resolveEntityParam`; every geoid's length
  matches its tier; no duplicate slugs; record count equals the DB count.

  ⚠ It derives its expectations **from the database**, never from a list of its
  own. A guard that keeps its own copy of the list cannot catch the list being
  wrong — the `CITY_TIER_TYPES`/`borough` lesson.

### Acceptance (from the note, consumer side)

1. `GET <host>/api/treasury/coverage` → 200, JSON, CORS-readable cross-origin.
2. A known city, county and state each appear with a correct geoid and a `slug`
   that, passed as `?entity=`, lands on that entity.
3. Every entity in the catalog resolves — no catalog entry produces the
   not-found state. **This is what `verifyCoverageCatalog.mjs` mechanises.**
4. `?entity=definitely-not-a-real-place-zz` shows not-found, not Bloomington.
   **Already satisfied by PR #158.**

## 7. Sequencing

The two repos land separately, in order:

1. **TT repo** — migration, backfill script, matcher tests, national backfill run.
2. **EV-Accounts repo** — `getCoverageCatalog()`, the public router, mounting
   order, endpoint tests. Cannot be built until the column has values.
3. **TT repo** — `verifyCoverageCatalog.mjs` against the live endpoint.
4. **A reply note to Civic Spaces** (§8).

Every change goes on a branch and through a PR; nothing is pushed directly to
`main`.

## 8. What must be told to Civic Spaces

1. **The federal slug is `united-states-us`.**
2. **Township geoids are 10-digit MCD codes and will not match a 7-digit
   place-FIPS slice.** They are correct data and belong in the catalog, but under
   their "no match, no row" rule the ~2,787 townships produce no Treasury row
   today — **Michigan will look absent to them even though its coverage is
   100%.** Geoid lengths are self-describing (2/5/7/10), so no extra field is
   needed, but they must not discover this by finding Michigan empty.
3. **Use the API origin directly**, not
   `treasurytracker.empowered.vote/api/...` — the TT host reaches the endpoint
   only via a static-site proxy hop, and they already talk to that API.
4. The catalog's public host for user-facing links is
   **`treasurytracker.empowered.vote`** — not `financials.empowered.vote`.

## 9. Explicitly out of scope

- **The Essentials `VITE_TREASURY_URL` contradiction.** Essentials defaults it to
  `https://financials.empowered.vote`, which is the EV Financials surface —
  `App.tsx` sets `isFinancialsHost`, retitles the page, and defaults the entity
  to `empowered-vote-ca`. So Essentials may send someone who asked for a city
  budget to a page branded as EV's own financials. Real, worth fixing, and
  orthogonal to this work. Tracked separately.
- **The `buildFlStatewideEntities.mjs` `exactMatchKey` collision.** Latent and
  unverified; this design avoids depending on it but does not repair it.
- **Enabling gzip API-wide.** A bigger win than the route-scoped version; its own
  decision.
- **A curated alias table** for abbreviation misses (`Mt.` vs `Mount`). Deferred
  until the national miss rate is measured.
- **`nonprofit`, `special_district`, `school_district`, `conservancy`,
  `library`** entity types — no geoid, out of scope, per the note.
